## Структура задачи <a name="task_structure"></a>

Каждую неделю в репозитории появляются задачи. Задача помещается в отдельную папку 
внутри папки `week_##/tasks/`.

Как правило, папка с задачей содержит минимальный набор файлов:

- `README.md` - файл с описанием задачи и требованиям к выполнению.
- `CMakeLists.txt` - файл для сборки непосредственно данной задачи.
- `<task_name>.cpp` - файл требующий реализации данного задания.
- `test.cpp` - файл тестов для задачи.

Разрешено изменять только файлы реализации `*.cpp`. В задачах, где можно создавать 
несколько файлов с расширениями `.h` и `.cpp` самостоятельно, будет отмечена такая
возможность в условиях.

Также в удаленный репозиторий следует отправлять только изменения файла реализации.
Остальные изменения будут игнорироваться.

При отправке задачи она тестируется, при этом в случае успеха задача засчитывается.

Файл тестов `test.cpp` может включать не все тесты. Тесты на сервере могут быть 
расширены.

При сборке задачи будут установлены флаги компиляции:

```sh
g++ ./task.cpp -O3 -std=c++20 -fsanitize=address,undefined -Wall -Werror -Wextra
```
- следовательно, целесообразно проверять своё решение с данными флагами.

## Система оценивания <a name="grading"></a>

Каждая задача имеет заданную ценность в баллах. Баллы за задачу можно найти в файле
[grading/deadlines.json](grading/deadlines.json). За правильное выполнение задачи
в срок до дедлайна начисляется **100 %**. За выполнение после дедлайна до окончания 
курса начисляется **30 %** баллов. Дедлайн, если не оговорено иное, устанавливается 
в **пятницу 23:59 по МСК** следующей недели после старта задачи.

Задача выполнена правильно, если решение проходит все тесты при отправке в удаленный 
репозиторий. Также, после истечения дедлайна следует убедиться, что вам начислены 
баллы в [таблице результатов](https://disk.yandex.ru/i/Hm9SfMDHhKCfpg).

При обнаружении списывания, баллы обнуляются у всех участников списывания.

Для выживания в Школе разработчика необходимо к окончанию последнего дедлайна
набрать **60 %** от максимального балла.

## Сборка <a name="build"></a>

Ниже приведена инструкция для сборки из терминала. Современные _IDE_ также работают
с `CMake` и при установке плагинов могут автоматически собрать проект и все тесты 
будут доступны. Для простоты можете использовать бесплатную _IDE VS Code_. Но поскольку
у всех _IDE_ разные, то при возникновении проблем: думайте сами, решайте сами.
Но, конечно, не возбраняется спросить преподавателей или сокурсников в чате.

Сборка осуществляется с помощью `CMake`. Для этого в корне репозитория присутствует
файл [CMakeLists.txt](CMakeLists.txt) содержащий соответствующие инструкции и, 
включающий вложенные файлы `CMakeLists.txt` в подпапках проекта.

По умолчанию опция сборки примеров (`*/examples/<name>.cpp`) отключена, что 
позволяет не загромождать рабочее пространство _IDE_ и сосредоточиться на задачах.

Сборка проекта представляет собой сборку тестов для задач. Все задачи включены 
в один проект. Для сборки проекта в папке `build/` из корня репозитория 
осуществляются следующие команды:

1. Настроить проект в папке `build/` и подготовить файлы для сборки:

```sh
cmake -B build
```
- в логах команды следует убедиться, что всё прошло хорошо и используется нужная 
  версия компилятора

2. Собрать проект используя файлы из папки `build/`: 

```sh 
cmake --build build
```
- ввиду отсутствия реализации решений, при сборке проекта целиком,
могут возникать ошибки. Поэтому часто будет удобно собрать только одну решенную
задачу. При этом при сборке необходимо указать конкретный исполняемый файл.

## Запуск тестов <a name="testing"></a>

### Запуск теста с помощью `run_tests.sh` <a name="run_tests"></a>

Собрать задачу и запустить тесты можно скриптом [run_tests.sh](run_tests.sh) 
из корня репозитория:

```sh
./run_tests.sh <task_name>          # одна задача, например ./run_tests.sh addition
./run_tests.sh addition rms         # несколько задач
./run_tests.sh week_01              # все задачи недели
./run_tests.sh --help               # справка
```
- скрипт сам выполнит `cmake -B build`, если проект ещё не настроен, 
  соберёт тесты задачи и запустит их. В конце будет выведена сводка по задачам.
- этот же скрипт используется для автоматической проверки задач в **_GitHub Actions_**.

### Запуск теста с помощью CMake <a name="tests_cmake"></a>

Для сборки отдельной задачи и запуска тестов необходимо выполнить следующую команду:

```sh 
cmake --build build --target test_<task_name>
./build/tasks/test_<task_name>
```
- `<task_name>` - имя задачи, которую требуется собрать.

### Ручной запуск теста <a name="tests_compiler"></a>

При необходимости можно экспериментировать с флагами компиляции.
Чтобы запустить тест вручную, можно выполнить следующую команду из корня репозитория:

```sh
g++ ./week_01/tasks/addition/test.cpp -lgtest -lgtest_main && ./a.out
```
- при этом библиотека **_GoogleTest_** уже должна быть собрана.
- аналогичную команду можно применить, если используется `clang++`

В тестирующей системе запуск производится со следующими флагами:

```sh
g++ ./week_01/tasks/addition/test.cpp -O3 -std=c++20 \
    -fsanitize=address,undefined -Wall -Werror -Wextra \
    -lgtest -lgtest_main \
&& ./a.out
```

## Запуск примеров <a name="run_exaples"></a>

Примеры рекомендуется запускать из терминала, так будет удобнее.

Находясь в корневой папке репозитория для запуска примера из терминала
необходимо выполнить одну из команд:

```sh
g++ ./week_01/examples/hello_cpp.cpp -std=c++20 -Wall -Wextra && ./a.out
```

```sh
clang++ ./week_01/examples/hello_cpp.cpp -std=c++20 -Wall -Wextra && ./a.out
```

При необходимости можно убрать, добавить или поменять флаги компилятора.

Порядок примеров в соответствии с ходом лекции можно найти в рабочей папке
соответствующей недели `week_01` в файле [CMakeLists.txt](week_01/CMakeLists.txt).
Цели обозначенные командой `add_example(...)` упорядочены последовательно.

## Сборка и запуск с санитайзерами <a name="asan"></a>

Обратите внимание, что на сервере осуществляется тестирование с включенными 
санитайзерами, которые проверяют наличие неопределенного поведения и некорректной 
работы с памятью в программе. Осуществить такую сборку можно следующими командами:

```sh
cmake -B build-asan -DCMAKE_BUILD_TYPE=Asan
cmake --build build-asan --target test_<task_name>
./build-asan/tasks/test_<task_name>
```

## Оформление кода <a name="code_style"></a>

Код решения следует оформлять по правилам из файла `.clang-format`:

- отступ 4 пробела
- фигурная скобка на той же строке
- строки не длиннее 120 символов
- и т.д.

Команда, позволяющая показать отличия форматирования без внесения изменений:

```sh
clang-format --style=file <path> | diff -u <path> -
```
- `<path>` - путь к файлу.

Для ручного управления форматированием отдельного файла или группы файлов
в соответствии с регулярным выражением, используется команда:

```sh
clang-format --style=file -i <path>
```
- `<path>` - путь к файлу.

## Отправка решения <a name="push"></a>

Перед тем как приступать к задачам, подтяните последние обновления курса 
(подробнее в [SETUP.md](SETUP.md)):

```sh
git pull upstream main
```

После того как локально все тесты проходят и проверен стиль код проекта, можно
отправить задачу в удаленный репозиторий для сдачи.

Для этого необходимо выполнить следующие команды `git` из корня репозитория:

```sh
git status                                           # посмотреть, какие файлы изменены
git add ./week_01/tasks/addition/addition.cpp        # добавить только файлы решения
git commit -m "add (solution): add <task_name> task" # сделать коммит с понятным комментарием
git push origin main                                 # отправить в свой удаленный репозиторий
```
- Добавляйте в коммит только файлы решений. Не используйте `git add .` без проверки 
  `git status`: так в коммит легко попадут лишние файлы.
- Сообщение коммита должно быть адекватным, для удобства рекомендуется
  использовать префиксы `add`, `fix`, `ref`, `del`, `upd`.
- Вместо `<task_name>` подставить имя задачи.
- Решения отправляются только в ваш приватный репозиторий (`origin`). Отправить что-либо
  в репозиторий курса (`upstream`) нельзя.

После чего необходимо пронаблюдать за пайплайном и убедиться, что задача решена
верно и зачтена.

## Проверка решения <a name="github_tests"></a>

После отправки (`git push`) в ветку `main` решение автоматически проверяется в 
**_GitHub Actions_** вашего репозитория:

- При каждой отправке в ветку `main` запускаются тесты тех задач, файлы которых
  были изменены. 
- В момент дедлайна автоматически запускаются тесты всех задач недели в ветке 
  `main`. Именно этот запуск определяет, сдана ли задача в срок. Поэтому перед
  дедлайном очень важно иметь актуальные решения именно в ветке `main`, если
  задачи каждой недели вы решаете в отдельных ветках.

Результат виден на вкладке **_Actions_** вашего репозитория:

- Зелёная галочка — тесты прошли.
- Красный крестик — есть ошибки.

В логе запуска видно, какие задачи собраны и какие тесты не прошли, а на странице 
запуска должна появиться итоговая таблица по задачам.

### Запуск тестов в удаленном репозитории <a name="github_action"></a>

В удаленном репозитории тесты можно запустить и вручную. 

Для этого во вкладке **_Actions_** вашего удаленного репозитория _GitHub_
нужно выбрать _workflow_:

- **_Testing Tasks_** - все задачи или конкретная неделя
- **_Testing Tasks Week ##_** - вся неделя или отдельная задача

После чего в основном окне появится кнопка **_Run workflow_**, где можно
выбрать ветку для тестирования и параметры запуска _workflow_

## Работа в ветках <a name="branch"></a>

Если вам удобно, задачи каждой недели можно решать в отдельной ветке, 
например `week_01`, `week_02`. Это больше похоже на реальную разработку.
Но для курса не обязательно и можно работать сразу в `main`.

> Засчитываются только решения в ветке `main`. Автоматическая проверка 
> в **_GitHub Actions_** запускается только при отправке в `main`, 
> и проверка в момент дедлайна тоже использует решения из `main`. 
> Поэтому до дедлайна обязательно перенесите решения в `main` и 
> выполните `git push origin main`.

Начать работу над задачами текущей недели:

```sh
git switch main                 # переключиться на ветку main
git pull upstream main          # получить задачи новой недели
git switch -c week_01           # создать ветку недели и перейти в неё
```

После чего вся работа происходит в ветке `week_01`. Затем отправлять в
удаленный репозиторий нужно непосредственно ветку в которой работали:

```sh
git add ./week_01/tasks/addition/addition.cpp
git commit -m "add (solution): add addition task"
git push origin week_01
```

Перенести решения в `main` и сдать:

```sh
git switch main
git merge week_01               # перенести коммиты из ветки недели в main
git push origin main            # после отправки запустятся тесты изменённых задач
```

После этого убедитесь на вкладке **Actions**, что запуск для `main` прошёл успешно.

Посмотреть, в какой ветке вы сейчас находитесь, можно командой `git branch`.
